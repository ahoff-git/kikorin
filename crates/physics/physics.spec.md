## crates/physics — Rapier2D/Rapier3D Physics World

### Purpose
Wraps Rapier (2D or 3D, chosen once at construction) for rigid-body simulation of ECS entities. The ECS world is the source of truth: physics bodies are derived from ECS collider data, never the reverse. Owns no entity IDs and defines no component schemas.

### Dimension — a construction-time setup parameter
`PhysicsWorld::new(gravity, dimension: Dimension)` picks `TwoD` (Rapier2D) or `ThreeD` (Rapier3D, the original behavior) once, for that instance's lifetime — there is no runtime switch. `PhysicsWorld` itself is a thin dispatcher (`lib.rs`) over two backends with byte-identical public methods: `two_d::PhysicsWorld2D` and `three_d::PhysicsWorld3D`. Every consumer (`crates/engine`) calls the same API regardless of which backend is active; nothing above `PhysicsWorld` branches on dimension.

- **`ThreeD`**: X/Z is the ground plane, Y is up — unchanged from before this crate had a 2D mode.
- **`TwoD`**: X is horizontal, Y is up (gravity applies to Y, same as 3D one dimension down) — there is no second horizontal axis. The ECS position/velocity/collider types stay `[f32; 3]`-shaped for parity with 3D and with the ECS `World`'s own storage (which this crate does not own and does not change); the 2D backend only ever reads index 0 (x) and index 1 (y). Index 2 (z) is never read for physics and is passed through unchanged on `sync_to_world` — whatever a caller last put there (e.g. a render depth/layering value) survives a physics tick untouched. Callers passing a 3-component `direction`/`to` (e.g. `cast_ray`) get a purely 2D interpretation: only x/y participate; z is ignored, not treated as depth. `floor_height_at(x, z)` keeps its two-argument signature for parity but `z` is meaningless in 2D and is ignored. Collider shapes drop `half_depth` (Rapier2D's `cuboid` takes only half-width/half-height); the ECS `ColliderConfig` itself is unchanged (still always carries `half_depth`, just unused when the physics world is 2D).

### Per-tick Flow
`sync_from_world(&world)` → `step(dt_secs)` → `sync_to_world(&mut world)` — identical in both backends.
- **sync_from_world:** reads `collider`, `position`, `is_floor`, `velocity` for all entities. Entities with no active `ColliderConfig` are removed from the physics world. Floor entities and sensors become fixed bodies; everything else dynamic with rotation locked.
- **Create-once contract:** bodies and colliders are built the first time an entity appears with an active config. Later `ColliderConfig`/`is_floor` mutations on a live body are silently ignored — the only rebuild path is deactivate (`active: false`, one sync) → reactivate.
- **sync_to_world:** writes position and `grounded` back for every non-fixed body and marks it `DirtyFlags::TRANSFORM` unconditionally each tick — even at rest, so resting dynamics emit TRANSFORM net patches at full tick rate (known over-dirtying tradeoff; a fix would compare translations before dirtying). In `TwoD`, this is where z gets read from the world and echoed back untouched (see Dimension above).

Out-of-tick queries (`floor_height_at`, `cast_ray`, `cast_ray_with_normal`, `cast_collider`) need the query pipeline populated; `step` rebuilds it each tick, but callers using these before the first step (e.g. navmesh construction) must call `prepare_queries()` first.

### Sensor Exclusion
Sensors are fixed bodies, so an is-fixed predicate alone would treat them as terrain. Every terrain-oriented query (grounded probe, `floor_height_at`, `cast_ray_with_normal`, `cast_collider`) also passes `exclude_sensors()` — a sensor is a trigger zone, not a surface: grounding on one, bouncing a bullet off one, or sampling a floor height from one would all be wrong. `cast_ray` (generic first-hit by entity) is the one query that still sees sensors. Applies identically in both backends.

### Velocity Split — game controls the horizontal axes, Rapier owns Y
`sync_from_world` writes ECS `velocity.x` (and `velocity.z` in `ThreeD`) to Rapier `linvel` every tick, but `velocity.y` only when its magnitude exceeds `Y_COMMAND_THRESHOLD` (0.01) — below that, "gravity owns Y". The engine stamps a latched jump impulse into `velocity.y` for exactly the consuming tick and resets it to 0 afterward (see the jump-latch invariant in the engine spec); between jumps Rapier's gravity-accumulated Y linvel is preserved. Lets game logic drive horizontal movement while Rapier handles vertical physics — identical policy in `TwoD`, just without a `velocity.z` to also forward.

### Grounded Detection
A short downward ray from the entity centre, max distance `half_height + GROUND_TOL (0.10)`; `grounded` is true iff it hits a floor entity (sensors excluded). A straight-down ray can only reach top/bottom surfaces — vertical side faces of stairs and walls are parallel to it and never hit — so side contacts cannot produce a false positive. Ray casts are expensive, so the probe runs only every `GROUNDED_STRIDE` (4) ticks and the cached value is served in between — `grounded` can be stale by up to `GROUNDED_STRIDE − 1` ticks. Same policy, same constants, in both backends.

### Zero Friction and Collision Groups on Dynamic Colliders
Dynamic colliders use `friction(0.0)` **and** `friction_combine_rule(Multiply)`. Friction 0 alone is insufficient: Rapier's default `Average` rule leaves `(0.0 + 0.5)/2 = 0.25`. `Multiply` wins by higher discriminant, giving `0.0 × 0.5 = 0.0`, eliminating tangential friction on stair/wall contacts that would otherwise oppose the jump impulse.

Dynamics are also placed in `GROUP_2` colliding only with `GROUP_1` (static terrain), so agent–agent contact pairs are never generated by the broadphase — eliminating O(N²) narrowphase work when agents cluster. Agent–agent avoidance is the engine's job (`apply_monster_separation`). This is game policy baked into the crate; a game needing agent–agent collision must change the group scheme here. Identical in both backends.

### Dependencies
`ecs` (World, ColliderConfig, DirtyFlags), `rapier3d` and `rapier2d` (parry re-exported through each). This crate is the sole physics integration — no TS Rapier bindings remain.

### Verification
`cargo test -p physics`:
- **3D backend** (21 tests, unchanged): gravity fall/landing (monotonic descent gated on contact, since depenetration nudges y up post-impact) and mid-air grounded=false; wall side-contact never grounds; velocity split — XZ reapplied every sync (proven by pin-against-wall-then-resume, since with zero friction/damping free motion cannot distinguish one-shot from per-sync application), zero and sub-threshold (|vy| ≤ Y_COMMAND_THRESHOLD) Y preserving gravity accumulation, above-threshold Y overriding it, non-zero Y as a one-frame jump impulse; grounded-cache staleness (stale up to GROUNDED_STRIDE−1 ticks after the floor vanishes); sensor exclusion — grounded survives standing inside a sensor volume, and `floor_height_at` sees through sensors to real terrain; the create-once collider contract (live config mutations are a no-op); `floor_height_at`, `cast_ray`, `cast_ray_with_normal`, `cast_collider` hit/miss and normals via `prepare_queries`; sensors neither block, contact, nor get dirtied; overlapping dynamics generate no contacts (collision-group filter); removal via inactive collider — queries miss, body freezes, `touching` stays stale until the next step; the dirtying contract (moving and resting dynamics dirty every tick, fixed never); and the `World::destroy_entity` Rapier-body leak, pinned as a known gap.
- **2D backend** (7 tests): the same physical shape of coverage scaled to what's dimension-specific — gravity fall/landing, wall blocking without setting grounded, `floor_height_at` hitting the top surface *and* proving `z` is ignored (two different z values, same result), `cast_ray` hitting known terrain, `cast_collider` reporting a wall normal with `z` pinned to 0.0, teleport ignoring `z`, and removed-body non-participation. One test (`two_d_cast_ray_hits_floor_and_z_survives_untouched_via_sync`) specifically proves a body's `z` component is never mutated by physics across many ticks of real 2D simulation.
